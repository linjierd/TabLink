# Offline browser receiver

The browser receiver uses HTTPS/WSS authenticated signalling followed by DTLS-SRTP video and an encrypted WebRTC data channel. It binds only the explicitly selected Windows IPv4 address. HTTPS defaults to TCP 27185; each session owns one UDP port from the exact set 27200, 27202, 27204, 27206, 27208, 27210, 27212, 27214 (SIPSorcery requires even RTP ports; RTCP is multiplexed). The default limit is three sessions and the hard limit is eight. No public relay, STUN/TURN, CDN, account or Internet access is required.

The initial CA certificate is generated per Windows user/install and its private material is encrypted by Windows DPAPI CurrentUser. Only the public `.cer` is exported. TabLink does not modify the Windows trust store or install trust on a device. The public CA fingerprint must be checked on the computer before trusting it on a receiver. Do not download and trust a replacement CA through an untrusted certificate-warning page. Transfer the public CA from the trusted computer first. iOS/iPadOS requires profile installation and then explicit full trust under Certificate Trust Settings. Android and Harmony browsers have their own certificate-installation policy. A managed device may prohibit user CA trust.

The pairing QR contains a random 256-bit token in the URL fragment. The frontend immediately removes it from browser history, sends it inside same-origin WSS, and never stores it. It expires after five minutes and is consumed once. Reconnection uses a new QR. Invalid Origin/token/profile cannot allocate a display or inject input. SDP fingerprints travel only through the authenticated TLS signalling channel. The browser itself validates the computer's TLS certificate against the manually trusted CA.

Choose 720p or 1080p, portrait or landscape, and 30 or 60 fps before connecting. H.264 is encoded as Baseline level 4.2, with an IDR interval of 30 or 60 encoded frames (one requested second; wall time depends on actual capture throughput). RTCP PLI/FIR suppresses dependent frames until the next fresh IDR; it never replays an old keyframe. Encoded frames flow directly from the bounded FFmpeg pipe into RTP without an unbounded application queue. These are requested capture settings, not a claim that every device can decode every setting. Start at 720p/30 on older devices.

Only `requestVideoFrameCallback` progress counts as a browser presentation report. Network delivery or keepalive messages do not count. A receiver lacking that browser API is rejected explicitly. No microphone/camera permission is requested. Input is confined to the owned display by the Windows callback, and the transport additionally blocks input while capture is paused or Windows is not on the available ordinary input desktop. A desktop switch retains the encrypted session while the existing capture recovery layer rebuilds the same verified display. Local retry grace is bounded; remote pause messages cannot extend it.

Windows requires the .NET 10 Desktop Runtime and ASP.NET Core 10 shared runtime for this framework-dependent build. WebRTC functionality and system fullscreen are browser dependent. Test results from Windows Chromium or a synthetic managed peer do not establish Safari, iOS, iPadOS or Harmony NEXT compatibility. Physical-device verification must be recorded separately.

Transport tests: `dotnet run --project tests/TabLink.Browser.Tests`. They use loopback TLS with an isolated temporary CA and no OS trust changes, firewall changes, virtual displays, ADB or live screen capture. Their transport fixture deliberately does not claim decoding. SIPSorcery is fixed at 10.0.16 and its exact license, notice and original NuGet metadata are under `third_party/sipsorcery/10.0.16`.
