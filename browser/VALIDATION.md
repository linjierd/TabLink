# Browser implementation validation — 2026-09-29

The Windows production project builds with zero warnings and zero errors. SIPSorcery is fixed at 10.0.16; the package and license hashes are recorded below. No test installed a CA in a system trust store, changed firewall rules, opened a virtual display, used ADB or captured desktop pixels.

## Automated transport tests

`dotnet run --project tests/TabLink.Browser.Tests/TabLink.Browser.Tests.csproj`

31 assertions passed. Coverage includes public-only CA export and DPAPI private storage; persistent CA identity; a correctly chained TLS leaf; rejection under ordinary TLS validation before manual trust; embedded assets, no-store and CSP; five-minute token format; idle WSS authentication timeout; wrong Origin/token and invalid profile before allocation; real ICE/DTLS/SRTP media transport; presentation-event and duplicate-report semantics; pause/input suppression and resume without fabricated presentation time; single-use pairing; W3C ICE candidate syntax and selected interface; three concurrent independent sessions and distinct approved UDP ports; capacity rejection; normal disposal and a deliberately late prepare callback after Stop; reduced-size RTCP PLI and malformed feedback; idempotent cleanup.

The managed transport fixture is deliberately non-decodable and is **not** evidence of browser H.264 rendering. Browser rendering was tested separately below.

## Production encoder and real Chromium decoding

Fixtures were generated by the **production** `H264Encoder.CreateSynthetic(..., browserCompatible:true)` using the bundled custom FFmpeg. This verifies the actual encoder argument path instead of duplicating it in a test script:

```powershell
dotnet run --project tests/TabLink.Video.Tests -- --browser-fixtures third_party/ffmpeg-tablink/bin/ffmpeg.exe tests/TabLink.Browser.Tests
dotnet run --project tests/TabLink.Browser.Tests -- --chromium-smoke tests/TabLink.Browser.Tests/baseline-synthetic.h264
dotnet run --project tests/TabLink.Browser.Tests -- --chromium-smoke tests/TabLink.Browser.Tests/baseline-1080portrait60.h264 1080 1920 60
```

Production NVENC output contained all 60 frames at 1280×720 / 30 requested fps and all 120 frames at 1080×1920 / 60 requested fps. Every SPS identifies Baseline, level 4.2.

Chromium QA used installed Google Chrome **153.0.8010.54**, headless, with a new isolated user profile. Its certificate exception was scoped to the exact test leaf's SPKI hash; no blanket certificate exception or installed trust was used. The test navigated to the real embedded client, selected its options, clicked Connect, and used real WSS, ICE, DTLS 1.2, SRTP, H.264 decoding and `requestVideoFrameCallback` reports.

| Fixture / requested mode | Last smoke decoded frames | Actual compositor-progress reports | Disconnect cleanup |
|---|---:|---:|---|
| 1280×720 landscape / 30 fps | 47 | 8 | Passed |
| 1080×1920 portrait / 60 fps | 65 | 8 | Passed |

These short smoke totals are **not sustained-fps benchmarks**. They verify compatible dimensions, decode, presentation progress, authenticated signalling and cleanup. They do not prove 60 actual fps, three concurrent physical displays, Safari/iOS/iPadOS, Android Chrome, HarmonyOS or HarmonyOS NEXT operation. Physical-device trust installation, browser fullscreen, real LAN/firewall traversal, touch placement and capture performance need separate field validation.

Two interoperability bugs were caught by the real browser test and fixed: SIPSorcery's `candidate` property omits the mandatory W3C `candidate:` prefix, and reduced-size browser PLI must be read through the parsed feedback object rather than reserialising a compound packet that requires SDES. Three-peer testing also confirmed that this library requires even RTP ports despite RTCP multiplexing, so the final exact eight-port set is 27200, 27202, 27204, 27206, 27208, 27210, 27212 and 27214.
